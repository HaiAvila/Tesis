## Networking today (Normcore)

- **Room:** the `Realtime` prefab in `Bootstrap.unity` joins room **`Test Room`** on start (its own "Join Room On Start" setting), on both roles. The `TesisEnsayo01` value in the scene is on a *disabled* `NormcoreDemoConnector` and isn't used. On the first `didConnectToRoom`, `Bootstrap` loads `MenuBackdrop` plus the role's home menu.
- **Disconnects:** Normcore's `AutoReconnect` is on the `Realtime` object (exponential backoff after a network error or the device sleeping). `Bootstrap` follows connect and disconnect for the whole session:
  - **Disconnect during Ensayo Remoto** → the user goes home with "Se perdió la conexión. Reconectando...". That means `Bootstrap.Mode == Remote` (from the Ensayo Remoto button through SceneSelect or the waiting screen and every take).
  - **Anywhere else** (menus, Inspección, Ensayar Solo) → nothing is interrupted, since those work offline.
  - **Reconnect** → only logged; no scene reload.
  - The director's home menu now shows notices too (`DirectorHomeMenuController.PendingNotice`).
  - An initial connection that never succeeds still leaves the app on the Bootstrap scene.
- **Take sync:** `sceneNumber` (property 5) + `shotNumber` (property 4) of `RehearsalSessionStateModel` (the transform hack is gone; the `RehearsalSession` object no longer has a `RealtimeTransform`, and its `RealtimeView` keeps component id 1 as deprecated).
  - The director writes both through `RehearsalSessionSync.SelectTake` → `RehearsalSessionState.SetSelection` (`RequestOwnership()`, then the scene, then the shot). Shot −1 = no shot; shot **0 = `FullSceneShot`, the whole scene** ("Escena completa"); scene −1 (or 0, in a room whose model predates the property) = unset.
  - The actor reacts to either change event, only in `Remote` mode, and reads the pair **one frame later**: sceneNumber can arrive after shotNumber in the same update, and going from one full scene to another changes only the scene.
  - Whatever the room already holds when joining doesn't fire the events, so a stale take never loads by itself. A late joiner reads both explicitly (see "Late join").
  - The actor takes the scene from the model; it only derives it from the shot in its own database when the model has no scene.
  - Locally the take is `Bootstrap.SelectTake(scene, shot)` → `CurrentSceneNumber`, `CurrentShotNumber`, `IsFullScene` and `StartShotNumber`: the shot whose `Shot{N}_Start` the take starts on, which for the whole scene is its lowest `shot_number` (1, 6, 11). `ShotStartPositioner`, `StartMarkAligner`, `StartMarkTape` and `FallGuard` use `StartShotNumber`. `[Escena]` logs.
- **Session state:** `RehearsalSessionStateModel` (`[RealtimeModel(createMetaModel: true)]`), with `sessionState`: 0 none, 1 active, 2 ended.
  - Written only by the director (`RequestOwnership()` and then set).
  - `BeginRemoteRehearsal` sets 1 and resets the take to scene −1 / shot −1. `EndRemoteRehearsal` sets 2 and is a no-op during Inspección.
- **Director leaves the rehearsal:** `sessionState = 2` → `RehearsalEnded` → the actor goes home with "El director terminó el ensayo".
- **Director disconnects:** Normcore clears the ownership the director held on the state model → `OwnerLeft` → the actor goes home with "Se perdió la conexión con el director". This only works once the director has written the state at least once.
- **Late join:** pressing Ensayo Remoto calls `JoinRemoteRehearsal()`, which loads the current take (a shot, or the whole scene with shot 0) only if the state is active **and** the model has an owner. A stale model left by a client that's gone is ignored.
- **Mode:** one local value, `Bootstrap.Mode` (`None` / `Remote` / `Solo` / `Inspect`), not synced. It replaces the old `IsInspecting` and `ActorJoinedRemoteRehearsal` flags; Ensayar Solo used to reuse the director's "inspecting" flag. It's set at every entry (home menu buttons, Favoritos → Ver) and reset to `None` at every exit (first connect, Menú Principal, the actor sent home, a disconnect during Remote). Pause → Selección de Escenas keeps the mode. Every director tool and every director-driven event checks for its own mode, so Solo shows no director tools and ignores the director entirely.
- **Solo session (actor):** `SoloSessionModel` (`[RealtimeModel(createMetaModel: true)]`, all properties reliable with change events) on its own `SoloSession` object (`RealtimeView` + `SoloSession` + `SoloRehearsalController`). Fields: `mode`, `sceneNumber`, `shotNumber`, `commandId`, `commandCounter`. The actor owns it only while in solo: when a take loads it writes mode=Solo + scene + shot (and writes again if the model arrives late or after a reconnect); on leaving solo it writes mode=None and clears ownership. Command channel with the same counter + baseline contract as the director's. It never touches the director's model. `[Solo]` logs. **Iniciar / Parar** on the right controller's B (A is the rig's stock Jump): each press sends the command; a world-space "Iniciando..." / "Detenido" fades out in ~1.5 s; opening the pause menu or leaving the take while running sends Parar automatically. Nothing is recorded on the Quest.
- **Actor head pose:** `ActorPositionSync` (actor build only). It's a `RealtimeTransform` that the actor requests ownership of every frame it doesn't hold it. The recorder reads it, and the avatar uses it as its root (below). `IsLive`: an actor build is writing it, i.e. owned by another client (or by this one on an actor build). A director can end up owning it too — seen in the Editor: owner = itself, parked at the origin — and that doesn't count as a head.
- **Actor avatar:** `AvatarPoseModel` (`[RealtimeModel(createMetaModel: true)]`) on a new persistent `ActorAvatar` object under Bootstrap: `RealtimeView` + `AvatarPoseSync` + `PodReceiver` + `PodAvatar`, with a Y Bot child (the body measurements copied from PodAvatarTest). **Whichever machine has the pods sends**, whatever its role: if `PodReceiver` hears pods there and `PodAvatar` solved at least one pod, it takes ownership and writes the final pose ~20 Hz — the local rotation of the 16 bones PodAvatar can move (hips, spine/chest/upper chest, shoulders, arms, legs, feet), 4 × int16 each, unreliable — plus once per calibration the avatar's size (root scale + 12 joint positions moved by the measurements) and which way the headset faced during the T-pose. Every other machine copies that onto its own Y Bot (eased) and hides it after 1.5 s without a pose; the viewer needs no calibration. PodAvatar's own floor and planted foot are switched off there (this places the avatar instead). Placed the same way everywhere: facing the T-pose's headset yaw (else the start mark's), the head bone turned by the headset and placed under it (8 cm behind the eyes; else over the start mark), the lowest sole on the set's floor (`SceneFloor`), so a squat lowers the hips. Shown only in content scenes, on director (and server) builds; the actor's own build hides it (`showOnActorBuild`). **Calibrar:** `SessionCommand.Calibrate` from the director — through Normcore to the pods machine, or on the director's own machine (new `RehearsalSessionState.CommandSentLocally`, since the sender never gets its own `OnCommand`) — or the Calibrar button in the `ActorAvatar` Inspector; ignored where there are no pods. The calibration phase is synced and every machine shows each pose as a `FloatingMessage` ("Calibración: ponte en T, palmas abajo" … "Calibración lista: 9 pods"). `[AvatarSync]` logs. **Checked in the Editor** (Director role, 9 simulated pods, connected to Test Room): 9/9 calibrated through `AvatarPoseSync`, the Editor took ownership and sent 112-byte poses + the 148-byte size, the sent pose decodes to the bones exactly, the lowest vertex sits at the floor (0.000), shown only once a content scene loaded. **Not yet checked:** a second machine receiving it (needs the Editor with the pods in one role and a Quest in the other — the director build shows the avatar, the actor build doesn't).
  - Known gaps: ~~the server build isn't separate yet~~ (done Nov 10: it doesn't write `ActorPositionSync` and follows the director's commands in any mode); the actor's Quest gets only the 1.5 s messages for the calibration, no countdown or pod buzz yet (part of the firmware batch); the pose isn't recorded with the take yet.
- **Who owns what:**
  - The director owns the shot transform and the state model.
  - The actor owns `ActorPositionSync`.
  - The machine with the pods owns `AvatarPoseModel` while it sends.
  - There's no presence model.
- **Command channel:** `commandId` + `commandCounter` on `RehearsalSessionStateModel`, written by the director (`RehearsalSessionSync.SendCommand` → `RehearsalSessionState.SendCommand`: id first, then counter + 1). Every other client fires `OnCommand` only when the counter goes above its baseline. The baseline is taken when receiving the model on joining and reset when the actor enters Ensayo Remoto, so a late joiner never replays an old command. The sender doesn't fire its own, and Ensayar Solo ignores commands (the baseline still moves up). Enum `SessionCommand`: Calibrate, Grabar, SiguienteToma, Accion, Corte, Guardar, Descartar, Aprobar. **Calibrate starts the pod calibration on the machine with the pods** (see Actor avatar); the others still only log (`[SessionSync]`). Temporary debug key on the director: **C** = Calibrate.

## Haptics today (pods)

- **Transport:** 9 pods → receiver XIAO → `Bridge/bridge.py` → UDP 5005 → `PodReceiver` (`Assets/Scripts/Haptics/`); cues go back as `C,<id>,<cue>,<param>` on UDP 5006. The BLE layer is verified on hardware; the firmware may be changed under the rules in CLAUDE.md. `Bridge/cue.py` sends cues by hand while the bridge runs (a second terminal: `<pod> <cue> [param]`, e.g. `0 3` = TRIPLE to every pod).
- **`PodReceiver` receive thread — fixed.** `Parse` runs on the UDP thread and used to call `Time.realtimeSinceStartup`, which is main-thread only: the first `P` line threw and the thread died, so orientation never reached Unity (a real bench run showed "0 de 0"). It now uses a `Stopwatch`, parses numbers with `InvariantCulture`, and catches anything a bad line throws so the thread keeps going. Raw quaternions are stored and converted on read, so changing `conversion` applies at once, even to a still pod. New `HasOrientation(id)`: false for a pod sending the all-zero "no IMU" quaternion.
- **Pod orientation reaches Unity — fixed with pod firmware v3 (mbed core).** The bridge logs of 2026-11-02 (pods 1 and 2, ~6,900 samples) were all exactly `0,0,0,1`, the pod's starting value: the BNO085 never answered. The user found why: the classic core's `Wire` doesn't work with the BNO085 (a plain IMU sketch prints nothing on it). `pod_v2.ino` v3 runs on the **mbed core with ArduinoBLE** as a peripheral; the receiver stays on the classic core with Bluefruit (ArduinoBLE holds only one central connection). Same UUIDs, notify and cue packet, so receiver, bridge and `PodReceiver` didn't change. v3 keeps the IMU watchdog: `0,0,0,0` while there's no reading, a failed IMU retried every 2 s, the report re-enabled after 1 s of silence and the IMU restarted after 5 s, slow blink only while readings arrive, each step on the pod's USB serial (pod-reference.md §3, §8, §11). Verified by the user: both pods seen moving in PodDiagnostics. Compiles with `Seeeduino:mbed:xiaonRF52840Sense`. **The 9/9, 6-minute stability test was done with Bluefruit pods and needs repeating with 9 v3 pods.**
- **`PodDiagnostics` scene** (`Assets/Scenes/PodDiagnostics.unity`, `PodDiagnostics.cs`): standalone, played on its own (no Bootstrap, XR rig or Normcore), desktop camera + IMGUI. One cube per pod with IMU readings, in a row by ID 1–9 (other IDs append to the right), each following `GetRotation(id)`, with red/green/blue sticks on its +X/+Y/+Z faces. The label "Pod N" always stays: white = readings, orange "sin IMU" = connected without a reading, grey = no data. On screen: connected/target (the receiver's `S` line), the IDs with data now, the ones without an IMU reading, and the current `conversion` — **C** (or a button) cycles it 0–3 at runtime. Buttons fire `CueCameraStart()` and `CueCut()` (checked on a UDP listener: `C,0,3,0` and `C,0,4,60`). Tested in Play mode with a fake bridge: an identity pod and a rotating one show cubes, an all-zero pod shows orange "sin IMU", a garbage line doesn't stop the thread, and a conversion change turns the cubes at once.
- **Axis flips in `PodReceiver`:** `flipX` / `flipY` / `flipZ` mirror a Unity axis after the conversion (`det(S)·S·v` on the vector part, so flipping X gives `(x, −y, −z, w)`: turns about Y and Z reverse, turns about X stay). One setting for the whole app. New read-only API for tools: `TryGetRawRotation`, `ToUnityRotation`, `GetPacketCount`.

- **Firmware v4 — battery, charge status, RSSI, calibration cues (2026-11-04).** Written in the user's other Claude session from a spec given here, compiled here against both cores (the mbed core resolves `nrf.h`, `NRF_P0`, `NRF_SAADC`; the classic core has `monitorRssi()`, `getRssi()`). PodAvatarTest and PodDiagnostics show each pod's values. **Checked in PodAvatarTest** (simulated pods and H lines, a listener on the cue port): the cue sequence and timing as above, FAIL only on a pod frozen on purpose, H cases normal / charging / low / older firmware / no RSSI all read right, malformed lines ignored. **`bridge.py`** checked with a fake serial port. **Not yet checked:** the full loop with the 9 real pods. Battery status for the director and the actor came later: see "Pod status".
- **Battery reading — checked** (built in v4 above; pod-reference.md §7, "Battery reading and charging pins"): Seeed's KiCad schematic gives VBAT → R16 1 MΩ → P0.31 → R17 510 kΩ → P0.14, no transistor or capacitor; with P0.14 OUTPUT LOW, P0.31 is 0.338 × VBAT = 1.42 V at 4.2 V (safe). ## The server `.exe` and the store of record (Nov 9-10, 2026)

**What it is.** `SERVER_BUILD` is now a real program: `Builds/Servidor/Servidor.exe` (Tesis → Build → Servidor (.exe); copy the whole `Builds/Servidor` folder to the PC with the pods). No headset, no menus, nothing to configure: it joins the room, reads the receiver on USB, and does what "the machine with the pods" already did (avatar, calibration, cue timeline). Everything server-specific is behind `SERVER_BUILD`, so the actor and director builds compile exactly as before, apart from the syncing below, which every role runs.

- **`Server/ServerApp.cs`** (added by `Bootstrap` in that build only): windowed 1280 × 720, runs in the background, XR stopped if it started, no home menu loaded (it stays in Bootstrap's scene). The window (screen-space, built in code): Sala (connected; actor's headset and director in the room or not), Receptor (USB), Pods n/9 with each pod's place, battery and signal, Calibración (the pose to do, or "Lista: 9 pods calibrados"), Toma (Ensayo Remoto / Ensayar Solo, scene and shot, "● Grabando", "Pistas hápticas en curso"), Tomas guardadas (how many, and what each device's sync is doing). On the right the actor's avatar from behind, on a floor disc, following where the actor walks (`AvatarPoseSync.onlyInContentScenes` off there). `FloatingMessage` goes to a line of the window on the server (no head to put it in front of); the camera isn't tagged `MainCamera`, so the headsets' head-locked indicators stay away.
- **`Server/SerialBridge.cs`: bridge.py inside the app.** Reads the receiver's USB serial port and feeds `PodReceiver.Feed`; cues go straight back through `PodReceiver.directCueOut`. Same line formats, untouched. Win32 through P/Invoke (the project's .NET Standard profile has no `System.IO.Ports`), overlapped I/O so a cue is written at once while a read waits. Finds the port by itself: the Seeed boards present on USB (vendor ID, from the registry), opened one at a time at 115200 with DTR on; the receiver is the one that sends `S,` status lines - a pod plugged in to charge has the same USB ID and never does (checked: COM14 was a pod, the log says so and leaves it alone for 20 s). Looks again when the port goes away or quiet (6 s). `-puerto COM7` on the command line skips the search. If another program holds the port (bridge.py, the Arduino Serial Monitor) the window says so. **`PodReceiver` still listens on UDP 5005**, so bridge.py keeps working on the server as a fallback; a second copy of the app on the same PC no longer throws when 5005 is taken, it warns.
- **Server-only behavior changes:** `ActorPositionSync` doesn't write a head and only counts as live a head owned by a machine that isn't a director's (a director's machine can end up owning it, parked at the origin - from the server that looked like an actor); `RehearsalSessionState` fires the director's commands in any mode (the actor's build only in Ensayo Remoto - the server was ignoring Calibrar and Siguiente toma).
- **`AppPaths.DataRoot`**: the database, audio, notes and exports go through it. The server `.exe` uses `persistentDataPath/Servidor` - on a PC that also runs the Editor both would otherwise share one `shotlist.db` while acting as two devices. `-datos <name>` (players) or `SessionState "Tesis.CarpetaDatos"` (Editor, forgotten when it closes) pick another folder, to test the syncing against copies.

**The store of record: `Sync/TakeSync.cs` over `Sync/SyncLink.cs`.** Every device's takes and cue timelines are kept the same as the server's, through Normcore, so it works with the director somewhere else.

- **Transport (`SyncLink`, `SyncPeer`, `SyncPeerModel`, `Resources/SyncPeer.prefab`)**: each machine creates its own `SyncPeer` on joining (like `VoiceClient`), with its role and a random peer id. A message is cut into 12 KB chunks; one chunk at a time sits in the sender's model, addressed to one peer, until that peer's model acknowledges it (state, not events: Normcore only promises the latest value). About 20 takes in 20 s. Each message carries a checksum; a damaged one is thrown away and the pass retried. **Found on the first two-process test:** Normcore reuses the `byte[]` of a property when the next value has the same length, so the chunks of a long message overwrote each other - each received chunk is now copied.
- **Stamps (`ShotListDatabase.Sync.cs`)**: `Sesiones.rev` (UTC ticks of the last change to the take or its preferida / favorita marks), `CueTrackRev` (per shot's timeline, which travels whole), `DeletedTakes` (so a deletion spreads instead of the take coming back). Every change made on a device stamps and raises `ShotListDatabase.Changed`; what arrives from another device is stored with the stamp it came with.
- **A pass** (device → server; the server only answers): catalog; deletions both ways; takes the server lacks are sent and takes the device lacks are fetched, whole (head track, camera, avatar, boundaries, set events), matched by GUID; marks and cue timelines: the newer stamp wins, and with equal stamps the server's copy stays - except a timeline made from the take that is the shot's preferida on the server, which replaces one that isn't. A new take arriving as preferida beats the shot's current one if its stamp is newer or, with equal stamps (takes from before syncing), if it was recorded later. Passes run when the server appears, 2 s after a local change, and when the server's `dataVersion` moves (another device changed something); never while a take is recording (`SyncLink.Paused`).
- **Not synced yet:** the takes' conversation audio and the voice notes (13 MB of WAV on the PC today) - they stay on the device that recorded them. Scene Select doesn't refresh by itself when a sync brings takes (reopen it).
